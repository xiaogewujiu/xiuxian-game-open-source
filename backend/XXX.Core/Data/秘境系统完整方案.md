# 秘境系统完整设计方案

## 一、系统概述

秘境是一个**单人自动探索玩法**。玩家在秘境开放时间内进入后，系统按固定 tick 间隔自动触发随机事件。秘境中不存在地图推进、探索进度、区域、层数、阶段等概念。

核心模型：**秘境 = 开放时间 + 组合进入消耗 + 单人状态锁 + 固定 tick + 两级随机事件池 + 临时收益池 + 结算规则**

## 三、进入流程

### 3.1 进入前置检查（按顺序）

1. **开放时间检查** — 当前时间是否在秘境开放时间段内
2. **每日次数检查** — 查询 `DungeonDailyRecordEntity`，当日已进入次数 < `DailyLimit`(1次)
3. **队伍状态检查** — 查询 `PartyMemberEntity`，玩家不能在任何队伍中
4. **玩法互斥检查** — 玩家 `BattleMode` 必须为 `Normal`（不能在离线挂机或其他秘境中）
5. **组合消耗检查** — 检查背包/货币是否满足全部进入消耗

### 3.2 进入事务（原子化）

使用 `SemaphoreSlim` 进程锁 + `db.Ado.BeginTran()` 数据库事务（复用 `BattleService.TryConsumeDungeonChallengeAsync` 的锁模式）：

1. 扣除组合进入消耗（道具通过 `IInventoryService.DeductItemAsync`，货币通过 `_playerAttributeService` 扣除）
2. 写入/更新 `DungeonDailyRecordEntity`（进入次数 +1）
3. 创建秘境实例实体
4. 创建秘境快照
5. 设置玩家状态为秘境占用
6. 开始自动探索

> **待确认：** 组合消耗的具体配置结构。当前代码中没有"组合消耗"的通用模型，需要新建。

### 3.3 幂等保护

- 玩家维度锁：`ConcurrentDictionary<string, SemaphoreSlim>`（复用离线挂机锁模式）
- 唯一约束：`PlayerId + DungeonId + EnterDate`（在 `DungeonDailyRecordEntity` 上已隐含）

## 六、自动探索 Tick 规则

### 6.1 Tick 配置

秘境模板新增字段：

```csharp
public int TickIntervalSeconds { get; set; }  // tick间隔秒数，如30/60/120
```

### 6.2 Tick Worker

新建 `DungeonInstanceWorker : BackgroundService`（复用 `OfflineBattleWorker` 模式）：

```
PeriodicTimer(TimeSpan.FromSeconds(2))
→ 每2秒扫描所有活跃秘境实例
→ 对每个实例检查是否到达 nextTickTime
→ 到达则执行一次tick
```

### 6.3 Tick 执行流程

1. 检查秘境实例状态是否为"运行中"
2. 检查当前时间是否超过秘境关闭时间
3. 如果超过关闭时间 → 强制结算
4. 如果未超过 → 从事件类型权重表抽取事件类型
5. 从该类型事件池中抽取具体事件
6. 执行事件（战斗/资源/宝箱/奇遇/空事件）
7. 写入探索日志
8. 更新 `lastTickTime` / `nextTickTime`

### 6.4 停机补算

恢复后计算应补 tick 数：

```
应补tick数 = floor((now - lastTickTime) / tickIntervalSeconds)
```

逐个 tick 补算，中途死亡则停止后续补算并结算。

### 7.5 两级随机流程

1. 从 `eventTypeWeights` 权重表中按权重抽取事件大类
2. 从该大类对应的 `eventPools` 中按权重抽取具体事件
3. 执行具体事件的逻辑（战斗/回复/加buff/加debuff/发奖励/触发奇遇等）

### 7.6 随机特性

- 每次 tick 独立随机，无冷却、无连续限制、无保底、无纠偏
- 允许连续出现相同事件
- 不参考上一次随机结果
- 特殊事件（如 event_weather_001 灵气暴涌）可以通过一个临时 modifier 字典影响后续 tick 的权重或奖励倍率

## 八、战斗事件流程

### 8.1 执行流程

1. tick 抽到战斗类事件
2. 读取秘境快照角色属性，构建 `BattleFighter`
3. 读取怪物配置（来自 `GameData.MonsterTemplates`），构建敌方 `BattleFighter`
4. 调用 `BattleSystem.StartBattle(playerSide, enemySide)` 真实战斗计算
5. 一次性模拟完整回合制战斗
6. 得到 `BattleResult`

### 8.2 战斗结果处理

**玩家胜利：**
- 从 `BattleResult` 获取 `ExpGained`, `GoldGained`, `DroppedItems`, `DroppedEquipments`, `DroppedCollections`
- 更新秘境快照中的 `CurrentHp`, `CurrentMp`（根据战斗日志中的最终状态）
- 所有收益写入**临时收益池**（不进真实背包）
- 写入战斗日志

**玩家死亡：**
- 进入死亡结算（见第十节）

### 8.3 自动用药

> **待确认：** 当前战斗系统 `BattleSystem` 是一次性模拟，不支持逐回合插入用药逻辑。

**方案：战斗后用药**

战斗胜利后，检查快照 HP/MP 是否低于阈值：
- 检查真实背包中是否存在配置的药品
- 有药 → 调用 `IInventoryService.DeductItemAsync` 真实扣除 → 恢复快照 HP/MP
- 无药 → 用药失败，不恢复

> 此方案简化了实现，但与初稿中"嵌入战斗模拟过程"的要求不同。如果需要逐回合用药，需要扩展 `BattleExecutor` 支持回调。

## 九、临时收益池和结算

### 9.1 临时收益池结构

> **待确认：** 当前代码中没有临时收益池的通用模型。需要新建。

建议新增实体：

```csharp
[SugarTable("DungeonRewardPool")]
public class DungeonRewardPoolEntity
{
    public string GID { get; set; }              // 主键
    public string InstanceId { get; set; }       // 秘境实例ID
    public string PlayerId { get; set; }         // 玩家ID
    public string RewardType { get; set; }       // Gold/Exp/Item/Equipment/Collection
    public string RewardId { get; set; }         // 道具ID/装备模板ID/空
    public int Quantity { get; set; }            // 数量
    public string Source { get; set; }           // 来源：Battle/Resource/Treasure/Adventure
    public bool DeathKeep { get; set; }          // 死亡时是否保留
    public DateTime CreateTime { get; set; }
```

### 9.2 结算规则

| 退出原因 | 收益处理 |
|----------|----------|
| 主动退出 | 临时收益**全部发放** |
| 秘境关闭强制结算 | 临时收益**全部发放**（与主动退出一致） |
| 死亡 | `DeathKeep=true` 的发放，`DeathKeep=false` 的丢失 |

### 9.3 发放流程

1. 读取临时收益池
2. 根据退出原因筛选可发放收益
3. 逐条发放：
   - `Gold` → `_playerAttributeService.AddGoldAsync`
   - `Exp` → `_playerAttributeService.AddExpAsync`
   - `Item` → `_inventoryService.AddItemAsync`
   - `Equipment` → `_equipmentRepository.AddAsync`
   - `Collection` → `_collectionService.GrantRandomCollectionItemAsync`
4. 生成结算日志
5. 清理秘境实例

## 十、死亡处理

### 10.1 死亡触发

- 战斗结果 `IsVictory = false` 且玩家 HP 归零
- 秘境快照 `CurrentHp <= 0`

### 10.2 死亡结算

1. 遍历临时收益池，`DeathKeep=true` 的发放，`DeathKeep=false` 的丢弃
2. 清除秘境占用状态（`ActiveDungeonInstanceId = null`）
3. 标记秘境实例为"已结束"
4. 进入消耗不返还
5. 今日进入次数不返还
6. 已消耗的药品不返还

### 10.3 无额外惩罚

- 不扣真实经验/修为/金币/道具
- 不扣装备耐久
- 不掉装备
- 不增加虚弱时间
- 不降低境界

## 十一、离线/停机规则

### 11.1 玩家离线

- 玩家下线**不暂停**秘境
- 秘境实例继续按 tick 推进
- 离线期间仍可能触发事件、战斗、自动用药、死亡、获得临时收益、强制结算

### 11.2 服务器停机

- 恢复后按离线时间补算所有错过的 tick
- 补算规则见第六节 6.4

### 11.3 玩家重新上线

- 如果秘境仍在进行 → 显示当前秘境状态/日志/临时收益
- 如果秘境已结束 → 显示结算结果/离线期间日志

- 使用 `ConcurrentDictionary<string, SemaphoreSlim>` 玩家维度锁

### 14.2 结算重复执行

- 秘境实例状态机控制：`Running → Settled`

- 支持重试（发奖失败时保持 `Running` 状态，下次 tick 重试）

### 14.3 发奖失败

- 单条奖励发放失败不中断整批结算
- 记录失败日志，后续可手动补发

### 14.4 服务器重启

- 启动时扫描所有 `Status=Running` 的秘境实例
- 根据 `LastTickTime` 补算 tick
- 根据开放时间判断是否需要强制结算

### 14.5 玩家状态卡死

- 定时检查：如果玩家有 `ActiveDungeonInstanceId` 但对应实例已结束 → 清除状态
- 如果玩家有 `ActiveDungeonInstanceId` 但实例不存在 → 清除状态

## 十七、玩家偶遇模块

### 17.1 模块概述

秘境中存在概率遭遇其他真实玩家的机制。当 tick 触发"玩家偶遇"事件时，系统从当前在同一秘境中运行的其他玩家实例里匹配一个，根据双方好感度决定交互方式：

- **好感度高** → 概率组队（临时队伍，共享后续事件）
- **好感度低** → 概率 PvP 战斗（快照对战）
- **中间区域** → 按好感度线性插值概率，随机判定

### 17.2 事件类型扩展

新增事件大类：

```csharp
public enum DungeonEventType
{
    // ... 原有10种 ...
    PlayerEncounter = 11  // 玩家偶遇
}
```

种子数据中新增"玩家偶遇"类事件：

| 事件ID | 事件名称 | 描述（前端展示文案） | EventDataJson |
|--------|----------|----------------------|---------------|
| encounter_friend_001 | 故人重逢 | 远处走来一个熟悉的身影，定睛一看，竟是一位旧识！你们相视而笑。 | `{"encounterType":"friendly","matchScope":"sameDungeon"}` |
| encounter_rival_001 | 狭路相逢 | 前方传来一阵脚步声，你警觉地握紧武器。转角处，一个身影出现在你面前——是敌是友？ | `{"encounterType":"random","matchScope":"sameDungeon"}` |
| encounter_mystery_001 | 神秘来客 | 一道身影从迷雾中走出，你看不清对方的面容。空气中弥漫着一股莫名的气息。 | `{"encounterType":"mystery","matchScope":"sameDungeon"}` |

### 17.3 匹配规则

当玩家偶遇事件触发时，匹配目标玩家的规则：

1. 查询所有 `Status == Running` 且 `DungeonId` 相同的秘境实例
2. 排除自己
3. 排除已组队的实例（有 PartyId 的）
4. 排除已死亡（CurrentHp <= 0）的实例
5. 如果没有可匹配的目标 → 降级为"空事件"，写日志"四周空无一人"
6. 如果有多个候选 → 随机选择一个

### 17.4 好感度概率计算

读取 `PlayerFavorabilityEntity` 获取双向好感度：

```
A→B 的好感度 = valueA
B→A 的好感度 = valueB
双向好感度 = (valueA + valueB) / 2
```

#### 好感度概率配置（可配置）

好感度概率阈值配置在秘境模板的 `EncounterConfigJson` 中，Admin 可自由调整：

```json
{
  "favorabilityTeamThresholds": [
    {"minFavorability": 1500, "teamRate": 80},
    {"minFavorability": 500, "teamRate": 60},
    {"minFavorability": 100, "teamRate": 40},
    {"minFavorability": 0, "teamRate": 20},
    {"minFavorability": -500, "teamRate": 5},
    {"minFavorability": -99999, "teamRate": 0}
  ],
  "defaultTeamRate": 20,
  "rivalPvpBonusAttack": 10
}
```

- `favorabilityTeamThresholds`：按好感度从高到低排列，匹配第一个满足 `minFavorability` 的阈值
- `defaultTeamRate`：无好感度记录时的默认组队概率
- `rivalPvpBonusAttack`：好感度 < -2000 时 PvP 对方攻击加成百分比

如果不存在好感度记录 → 使用 `defaultTeamRate`。

概率判定后：
- **组队成功** → 进入组队流程
- **组队失败** → 进入 PvP 流程

### 17.5 PvP 战斗流程

1. 读取双方秘境快照（SnapshotJson）
2. 构建双方 BattleFighter（FighterType.Player）
3. 调用 `BattleSystem.StartBattle(playerSideA, playerSideB)` 真实 PvP 战斗
4. 处理结果：
   - **发起方胜利**：
     - 按掠夺配置从对方临时收益池中掠夺奖励
     - 被挑战方进入死亡结算（deathKeep=false 的收益丢失）
     - 写入双方战斗日志
   - **被挑战方胜利**：
     - 按掠夺配置从发起方临时收益池中掠夺奖励
     - 发起方进入死亡结算
     - 写入双方战斗日志
   - **平局（MaxRounds=50 耗尽）**：
     - 双方各损失 10% 当前 HP
     - 各自继续探索，无其他影响

#### PvP 掠夺配置（可配置）

掠夺规则在秘境模板的 `EncounterConfigJson` 中配置，Admin 可自由调整：

```json
{
  "pvpPlunderConfig": {
    "currencyTypes": ["Gold", "SpiritStone", "Exp"],
    "currencyPlunderRate": 30,
    "equipmentPlunderCount": "1-3",
    "itemPlunderCount": "1-3",
    "equipmentPlunderRate": 50,
    "itemPlunderRate": 50
  }
}
```

- `currencyTypes`：可掠夺的货币类型列表（Gold/SpiritStone/Exp/Honor 等）
- `currencyPlunderRate`：货币掠夺比例（%），从对方对应货币收益中按比例掠夺
- `equipmentPlunderCount`：装备掠夺数量区间（如 "1-3" 表示随机 1~3 件）
- `itemPlunderCount`：道具掠夺数量区间
- `equipmentPlunderRate`：装备掠夺概率（%），不是 100% 必得
- `itemPlunderRate`：道具掠夺概率（%）

掠夺逻辑：
1. 从对方临时收益池中筛选 `DeathKeep=false` 的收益
2. **货币类**：按 `currencyPlunderRate` 比例从对方货币收益中扣除，加到自己收益池
3. **装备类**：按 `equipmentPlunderRate` 概率判定是否掠夺，成功则从对方装备收益中随机取 `1~equipmentPlunderCount` 件
4. **道具类**：按 `itemPlunderRate` 概率判定是否掠夺，成功则从对方道具收益中随机取 `1~itemPlunderCount` 件
5. 掠夺的收益写入胜利方的临时收益池（deathKeep=true，确保掠夺所得不会因后续死亡丢失）

### 17.6 组队流程

1. 创建 `DungeonPartyEntity`（秘境临时队伍）
2. 将双方实例的 `PartyId` 设置为新队伍 ID
3. 发起方设为队长（`IsPartyLeader = true`）
4. 记录组队日志到双方探索日志
5. B 玩家下次查看秘境状态时看到组队提示

### 17.8 组队后的事件共享机制

组队后，事件触发逻辑变更：

1. **只由队长的 tick 触发事件**（队员的 tick 跳过事件触发）
2. 所有事件结果对全队生效：
   - **战斗事件**：全队共同出战（所有队员的 BattleFighter 加入战斗），收益全队共享
   - **资源/宝箱事件**：收益写入全队每个成员的临时收益池
   - **回复事件**：全队共享回复（每个队员的 HP/MP 都恢复）
   - **增益/减益事件**：全队共享（每个队员都获得相同的 buff/debuff）
   - **奇遇/商店事件**：全队共享（触发结果对全队生效）
   - **空事件**：全队共享日志
3. **物品掉落分配**：装备和道具随机分配给队伍中的一名成员（写入该成员的临时收益池）
4. **玩家偶遇事件**：组队后不再触发（已组队的实例被排除在匹配池外）

### 17.9 组队状态下的死亡和退出

- **队员死亡**：队员退出队伍（PartyId = null），进入个人死亡结算。队长继续探索。
- **队长死亡**：队伍解散，所有队员 PartyId = null。队长进入死亡结算。队员各自继续探索。
- **队员主动退出**：队员退出队伍，结算个人收益。队长继续探索。
- **队长主动退出**：队伍解散，所有队员各自结算并退出。
- **秘境关闭强制结算**：队伍解散，全队各自结算。
